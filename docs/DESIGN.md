# reviewWork 前端设计要求

本文件记录用户已确认的前端设计方向，以已认可的开发者结果页为基准。产品业务规则参照 [SPEC.md](SPEC.md)，样例数据参照 [TEST.md](TEST.md)。

## 1. 已确认的设计原则

- 产品名称统一使用 **reviewWork**，保留大小写；页面品牌和浏览器标题保持一致。
- **必须 minimal。所有不必要的内容和操作都删除。** 不为填满页面增加卡片、导航、图标或说明。
- 界面使用英文，设计文档使用中文。
- 界面配色使用黑、白和中性灰；不使用绿色主题、彩色状态标签、渐变或装饰性色块。用户上传的原始证据保留原色。
- 以内容、表格和细分隔线组织页面，保留适当留白。原始反馈和审核操作是核心。
- 默认只展示完成当前任务所必需的信息；完整答案、证据和审核理由按需展开。
- 简化视觉不等于删除必要的业务校验、错误提示、登录或付款确认。

## 2. 参考与取舍

用户提供的参考截图为 `016-ecommerce-product-list-1.webp`，展示 Shadcnblocks Admin Kit 的商品列表。

采用其白底、黑色主操作、浅灰表头、细边框、紧凑筛选工具栏和清晰表格行的视觉语言。参考图中的电商业务、复杂侧栏、全局搜索、通知、主题切换与多级导航不属于本产品的页面需求，不照搬。

设计依据是用户提供的截图及随后认可的结果页；未通过 Mobbin MCP 获取参考，不将 Mobbin 研究标为已完成。本文件记录的最新视觉要求替代 SPEC 中尚未落实的设计研究安排；其他业务规则仍以 SPEC 为准。

## 3. 技术与实现约定

- 代码位于 `frontend/`。
- 使用 Next.js App Router、React、TypeScript、shadcn/ui 和 Tailwind CSS。
- 结果页相关页面逻辑、样式和 mock API 适配器位于 `frontend/result/`。
- 使用语义化表格、表单、按钮和可访问的 Dialog / Sheet；组件按需使用，不要求把所有组件都放到页面上。
- 页面样式限定作用域，避免影响其他页面；不得为单页主题修改其他页面的布局。
- 任务名称、题目、选项、金额、答案和统计来自数据接口，不能在展示组件里写死样例内容。

## 4. 开发者结果页

路由：`/tasks/[id]/results`。

### 4.1 默认布局

按以下顺序展示，不使用侧栏或多层页签：

1. **顶栏**：`reviewWork / Results`，右侧放 Developer login；登录后提供 Sign out。
2. **页面标题**：Results，下面一行显示任务标题。
3. **单行统计**：提交数量、待审核数量、剩余预算；旁边简短标明 demo / 模拟付款。不要拆成大号统计卡片。
4. **反馈概览**：桌面端两列，左侧答案分布，右侧简短 AI 总结；窄屏上下排列。
5. **提交列表**：一个搜索框、一个状态筛选、表格与分页。

### 4.2 答案分布与 AI 总结

- 通过选择框切换题目，动态显示该题所有选项，包括零票选项。
- 使用中性灰细条展示分布，配合数量和百分比；零提交时显示零，避免除零。
- 默认统计所有正式提交的最新答案，明确标注统计范围。列表搜索和状态筛选不改变概览统计范围。
- AI 总结使用简短文字，提供返回原提交的来源入口；不再嵌套彩色卡片、重复小标题或装饰图标。
- AI 只辅助审核，不能自动接受、拒绝或付款。AI 生成中或失败不能阻止查看原文与人工确认。

### 4.3 提交列表与详情

桌面表格保留以下列：

| 列 | 内容 |
| --- | --- |
| Participant | 提交者名称、提交编号 |
| Answer | 回答摘要，完整内容在详情查看 |
| Evidence | 证据文件数量和查看入口 |
| Status | 审核状态，以文字和中性灰标签表示 |
| Payment | 独立的付款状态，模拟付款明确标注 |
| 操作 | Review 或 View |

- 点击提交者、回答、证据入口或 Review / View，打开提交详情。
- 详情包含所有题目的选项与完整回答理由、原始证据、AI 审核说明、已有的发布者审核理由、付款状态与确认按钮。
- 截图可放大查看；视频按数据类型提供播放。示例证据必须标为 demo，不能伪装成真实上传。
- 支持 `?submission=<编号>` 定位详情。
- 详情内容可滚动，关闭按钮始终可用；关闭后恢复合理的键盘焦点。
- 不因反馈负面、未完成体验或 AI 尚未完成而禁用人工审核。

### 4.4 登录、确认与付款

- 开发者登录入口直接放在结果页，无需跳转独立登录页面。
- 未登录时尝试确认，先打开登录弹窗；登录后回到原提交的确认流程。
- 确认弹窗展示收款人、具体金额、预算变化和模拟付款说明。
- 确认期间禁用重复操作；成功后更新提交状态、付款状态和剩余预算。
- 预算不足时保持原状态并显示原因。重复确认不能重复支付；零报酬任务显示无需付款。
- 审核与付款状态分开表达。不得把已确认直接等同于真实付款成功。

### 4.5 明确删除的内容

当前结果页不再展示：

- 侧栏、工作区切换、重复面包屑和多层导航。
- 宣传标语、品牌装饰、彩色头像、营销卡片和装饰性页脚。
- 大号统计卡片、预算进度装饰、重复统计数字区块。
- Overview / Submissions / Task details 页签和独立任务详情板块。
- Copy results link、Export CSV、帮助弹窗等非当前审核流程必需的操作。
- 多套重复的状态筛选控件。

后续增加内容前，先判断它是否直接服务当前核心任务，不因组件可用就添加。

## 5. 视觉与响应式

- 白色页面背景，主文字接近黑色，次级文字使用可读的中性灰。
- 主操作使用黑底白字，次级操作使用白底细灰边框。
- 边框与行分隔线使用浅灰，表头使用极浅灰；避免大面积阴影和层层包裹的卡片。
- 使用普通无衬线字体，标题、正文、辅助信息有清晰层级；不依靠极小字号压缩信息。
- 状态必须有文字，不仅依赖颜色；焦点状态清晰，表单控件有可访问名称。
- 手机端概览改为单列，提交表格改为简洁的逐条布局，保留答案、证据、审核状态、付款状态与操作。
- 页面本身不得横向溢出；弹窗适应视口高度，支持键盘关闭和内容滚动。

## 6. 当前 mock 边界

当前阶段按用户要求 mock API call，不代表已接入后端：

| 适配函数 | 预期接口 |
| --- | --- |
| `getTask()` | `GET /api/tasks/:id` |
| `getResults()` | `GET /api/tasks/:id/results` |
| `approveSubmission()` | `POST /api/submissions/:id/approve` |

- 当前登录是本地 demo 会话，不验证真实身份，不发送邮件。
- 当前结果是样例数据，确认结果在浏览器本地保存；付款不会调用 Stripe，也不会移动真实资金。
- 保留已有的请求补充、拒绝、待付等状态展示，但不虚构未提供的写入接口。
- 后续接入真实 API 时，身份归属、预算事务和幂等必须由服务端保证；浏览器 mock 的校验不能代替后端保障。
- mock 与真实 Stripe Sandbox 的成功状态必须区分。当前设计简化不改变 SPEC 中的生产业务约束。

## 7. 验收要求

- 页面及浏览器标题使用 reviewWork，界面采用黑白中性灰。
- 无侧栏、彩色卡片、宣传文案、重复导航或已删除的辅助操作。
- 提交数量、动态答案分布、AI 总结及其来源可查看。
- 搜索、状态筛选、分页、详情与证据预览可用。
- 页内登录后可继续确认；刷新后 mock 确认结果仍保留。
- 重复确认、预算不足、零报酬处理正确。
- 加载、错误重试、无匹配结果和 AI 不可用状态可理解且不阻断无关操作。
- 桌面与手机均能查看并操作；详情关闭按钮可见，无页面横向溢出。
- 修改后通过相关单元测试、浏览器交互验证、TypeScript 检查和 Next.js 构建。
